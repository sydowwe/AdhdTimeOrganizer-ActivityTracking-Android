# Android tracker — review, 2026-11-10

A one-pass review of UX, functionality, code and security at `2452734` (version 1.7.0, code 10), with the
uncommitted status-screen title change in the tree.

**How it was done.** Read: the manifest and build config, the sync core (`SyncEngine`, `Outbox`, `BatchSender`,
`UsageStatsCollector`, `SessionBuilder`), auth (`RetrofitClient`, `TokenRefresher`, `RefreshPolicy`,
`AuthPreferences`, `KeystoreCipher`), the watcher, the monitors (break, drift, ramp, budget, loop), push, capture,
pause, the widget, the update check, and the status / login / settings screens. Ran `testDebugUnitTest` (546 tests,
all pass) and `lintDebug` (1 error, 121 warnings).

**What it does not cover.** The mapping, review and ignore screens, the internals of the pure policies, and the two
release scripts were only skimmed. **None of the bugs below was reproduced on a device**: each comes from reading
the code. Two claims rest on platform behaviour recalled rather than checked: the ~10 s limit for a
notification-action broadcast (item 4), and Robolectric being able to open Room (*Code and process*).

**Overall.** The core is in good shape: session building, the outbox and its cursors, the refresh policy and the
pure policies are careful and well tested. What is worth improving is at the edges: one latent release-only crash,
a few robustness holes, and a status screen that has outgrown its layout.

## Fix first

Ordered by damage if it happens. Items 1, 3, 5, 6 and 7 are a few lines each; 2 and 4 need a decision on behaviour.

### 1. Latent crash loop on release builds: `BudgetFacts` has no R8 keep rule

- **Where:** `app/proguard-rules.pro`; `budget/BudgetPreferences.kt:26`; `budget/BudgetMonitor.kt:77`;
  the classes are in `budget/BudgetTracker.kt:16-41`.
- **What:** `BudgetFacts` and `PhoneBudget` are stored as Gson JSON in the `daily_budgets` prefs. The rules file keeps
  `PendingIgnoreOp` and `KeptBlock` for exactly this reason ("renamed fields would make an updated app unable to read
  what the previous one wrote"), but not these two.
- **Trigger:** a release that adds, removes or reorders a field in either class. R8 then names the fields differently,
  and the JSON the previous build wrote can read back with `budgets == null`.
- **Effect:** `BudgetMonitor.install` reads `facts?.packages` inside `Application.onCreate`, outside any try. `packages`
  is `budgets.flatMapTo(...)`, so a null `budgets` throws there, on every process start, and nothing ever clears the
  prefs. Debug builds are not minified and never show it — and the phone on the desk runs debug builds.
- **Fix:** keep both classes in `proguard-rules.pro`, and make `install` tolerate unreadable figures (a try/catch that
  falls back to an empty set). Worth a sweep for any other non-DTO class a later feature stores as JSON.

### 2. A server or proxy that answers 400 to everything empties the outbox

- **Where:** `sync/BatchSender.kt:70`; `ResponseClassifier` in the same file; `SyncEngine.sendAll`.
- **What:** 400 / 413 / 422 is read as a payload complaint. The batch is bisected down to single sessions and each
  refused single is deleted (`dao.delete`).
- **Risk:** a bad server deploy, a WAF, or a reverse proxy's own 400 / 413 is indistinguishable from a payload
  complaint. One such period deletes everything queued — up to 50 000 sessions — at roughly 400 requests per 200-session
  batch. CLAUDE.md already refuses to drop on a 404 for this reason; the same argument applies to a blanket 400.
- **Fix, either or both:**
  - A circuit breaker: once more than a few singles are refused in one run, stop and wait. A server refusing
    everything is broken; the data is not.
  - Treat a 400 as a payload complaint only when the body is the server's own problem shape.

### 3. A lost Keystore key is a silent sign-out, or a startup crash

- **Where:** `data/local/AuthPreferences.kt:55` (`load`); `notify/SyncBlockedDecider.kt:70`;
  `auth/KeystoreCipher.kt:27-36`.
- **Silent sign-out:** when the stored tokens can't be decrypted, `load` returns null and no `signOutReason` is
  written. `SyncBlockedDecider` reads a null reason as "never signed in — setting up, not blocked", so no
  notification is posted, and `LoginActivity` shows no explanation. The tracker stops sending and says nothing.
  **Fix:** when `tokens` exists but won't decrypt, clear it with `SESSION_ENDED`.
- **Crash:** `decrypt` catches `GeneralSecurityException` and `IllegalArgumentException` only. A `ProviderException`
  (a runtime exception the Keystore provider can throw) or an `IOException` from `KeyStore.load` escapes into
  `AuthPreferences`' constructor, which runs from `RetrofitClient.init` in `Application.onCreate`. **Fix:** catch
  `Exception` in `decrypt`; decide what `encrypt` failing should do at sign-in (an error on the screen, not a crash).

### 4. Notification buttons do network work inside `goAsync()`

- **Where:** `breaks/BreakMonitor.kt:92`, `drift/DriftMonitor.kt:102`, `ramp/StartRampMonitor.kt:104-112`,
  `push/PushActionReceiver.kt:36`; timeouts in `data/api/RetrofitClient.kt:32`.
- **What:** the Break, Drift and Start-ramp receivers hold their `PendingResult` until the monitor's job ends, and that
  job also runs `evaluateSafely` → `NowClient.get` (and, for the ramp's Not this one, `skip-block` first). The push
  receiver holds it for the action POST. The KDoc on each `onAction` says the job "ends once the state is written";
  the code goes on past that.
- **Risk:** the connect timeout is 15 s and a refresh can add a 6 s wait, against a limit of about 10 s for these
  broadcasts. On a slow network the system can kill the process, which takes the foreground watcher with it.
- **Fix:** finish the broadcast as soon as the state is written and let the evaluation run on in the monitor's scope.
  For the push action and the ramp's planner calls, either a short `withTimeout` or a network-bound work request.

### 5. The watcher's poll loop has no exception handling

- **Where:** `watch/ForegroundWatchService.kt:120` (`poll`), launched on a scope with a `SupervisorJob` and no handler.
- **What:** a throw from `queryEvents` or the tracker is an uncaught exception on `Dispatchers.Default`: the app
  crashes. A sticky restart from the background may then be refused, leaving nothing watching until the next sync
  re-arms it.
- **Fix:** try/catch around each read (skip that read, keep the loop), as `ForegroundWatcher.dispatch` already does
  for listeners.

### 6. Quick capture loses the typed text on a configuration change

- **Where:** `capture/CaptureActivity.kt:41-42`; its manifest entry has no `configChanges`.
- **What:** a recreated activity (`savedInstanceState != null`) just finishes. Rotating the phone, or the system
  switching dark mode or font size, drops the dialog and the half-typed thought — the one thing the feature exists
  to prevent.
- **Fix:** `android:configChanges` on the activity so it isn't recreated, or save and restore the field.

### 7. Lint fails on `strings.xml:228`

- **What:** `budget_card_hint` contains `80 % and`, which lint reads as an invalid format string
  (`StringFormatInvalid`). The string is only set from the layout, so nothing crashes today.
- **Why it matters:** it is the single error among 121 warnings, so `lintDebug` exits 1 and can't be used as a gate.
- **Fix:** write the percent sign as `%%`.

## Security

**What is right.** HTTPS-only in release; tokens AES-GCM-encrypted with a Keystore key and written with `commit()`;
backup and device transfer exclude everything; the HTTP logger is `BASIC` in debug and off in release, never `BODY`;
every receiver is unexported; PendingIntents are immutable; the update download and a push's route are both held to
the build's own host; the signing secrets are guarded by a hook.

**What to tighten.**

- **Google sign-in sends no nonce** (`auth/GoogleSignIn.kt`, the `GetSignInWithGoogleOption`). A captured ID token can
  be replayed to `auth/tracker/login/google` for its lifetime. A server-issued nonce, set on the option and checked
  by the server, closes that. Needs a server change.
- **`CaptureActivity` is exported and saves an `ACTION_SEND` with no confirmation.** Exported is required for the share
  sheet, but it means any installed app can silently put to-dos in the user's Inbox. Low risk. An "Undo" on the toast
  would cover it without adding a tap.
- **An offline sign-out never revokes the refresh token on the server.** The logout call and the push unregister are
  fire-and-forget on `GlobalScope` (`MainActivity.kt:631`); if they fail, the server-side session lives until it
  expires. Queue them as network-bound work, as push registration already is. This also removes the `GlobalScope`.
- **The first sync uploads the previous 7 days** (`Constants.FIRST_RUN_BACKFILL_MS`), and the outbox records while
  signed out. Nothing on first run says so. One sentence on the setup screen: what is sent (package, label, times),
  what never is (notification text), and that the last week goes with the first sync.
- **`JwtSubject` reads `sub` with a regex.** It is used only to notice an account switch, never for trust, so this is
  a tidiness point: Gson is already a dependency and would parse the payload properly.
- **Not recommended:** certificate pinning. The server is self-hosted with rotating certificates; a pin is more likely
  to lock the phone out than to stop an attacker.

## UX

- **The status screen is one scroll of about 13 cards, and sync health is at the bottom.** Order today: banners,
  pause, quick capture, evening review, breaks, start ramp, drift, daily limits, time chime, loop check, ignored apps,
  sync status, backend, then Sync Now and Sign Out. The thing the app exists for — is it recording, when did it last
  send, how much is waiting — sits under ten feature cards. Suggested shape:
  - A one-line health summary at the top ("Recording · last sent 4 min ago · 0 waiting"), tapping through to the
    detail.
  - The nudges on their own screen, as a compact list of switches, each opening its settings.
  - Sign Out in settings, behind a confirmation that names the unsent sessions.
- **A nudge that can't fire still shows its switch on.** Every monitor turns itself off when its channel is muted or
  notifications are off, and `ForegroundWatcher.watch` returns `false` from the background without the battery
  exemption. The card says nothing either way. A small line per card — "Notifications for this are muted", "Needs the
  battery exemption to notice apps" — would explain a nudge that never comes.
- **Today's numbers exist only on the widget.** `TodaySummary` (total, top apps) and the pickups `PickupCounter`
  already has could head the status screen. It would give the app a reason to be opened, and it is the "pickups on
  the phone's own status screen" idea from `docs/ideas.md` #4.
- **Wording.** "Sync enqueued", "Backend: Connected / Unreachable" and "Backend Connection" are developer words.
  "Sync started", "Server reachable" and so on read better.
- **Language.** Nine strings are hardcoded in layouts (lint's `HardcodedText`), and the app is English-only while the
  server's pushes arrive in the user's language, so one notification shade mixes two languages.
- **Sign Out is one tap, no confirmation**, at the bottom of a long scroll next to Sync Now.
- **Login has no link to register or reset a password** on the web app.
- **After a sign-out, nudges and the watcher run on until the next sync** (up to 15 min): `performLogout` clears the
  tokens, the pushed notifications and the widget, but kicks no monitor. Kicking each one would withdraw what is
  showing at once.

## Functionality gaps

- **Six features have never been seen on a device**, by CLAUDE.md's own account: the widget, the pause tile,
  notification interruptions (event 12), push, pause, and the update check. The app also logs nothing, by design. So
  when one of them misbehaves on the MIUI phone there is nothing to look at.
  **Recommendation: build a privacy-safe diagnostics screen before building more features** — a ring buffer of
  decisions with no names ("drift: held, DND"; "ramp: alarm fired 40 s late"; "watch: start refused"), plus the
  "Copy diagnostics" export already listed under *Smaller ideas* in `docs/ideas.md`. It turns each "not yet seen on a
  device" into something that can be checked off.
- **OEM battery killers and app hibernation**, both already in `docs/ideas.md`. They deserve promoting: on a Xiaomi,
  for an app that is rarely opened, they are the likeliest cause of silent data loss, and the battery-optimization
  exemption alone doesn't cover MIUI's autostart setting.
- **`NowClient` doesn't remember a failure** (`now/NowClient.kt:32`). After a sync on a connected-but-dead network,
  the break, ramp, drift and budget monitors and the widget each wait out their own timeout on `/now`, one after the
  other. Remembering a failure for 10–30 s makes that one wait.
- **`Pauses.start` checks and inserts without a transaction.** The tile and the card racing could leave two
  overlapping pauses, and Resume ends only the latest. Unlikely (the dialog is modal); a `@Transaction` closes it.

## Code and process

- **No CI.** There is no workflow in the repo; tests run only when `test-release.ps1` or a person runs them. A
  workflow running `testDebugUnitTest`, `lintDebug` and an unsigned `assembleRelease` on every push would catch R8
  problems like item 1 and keep lint usable.
- **No migration test.** CLAUDE.md says the JVM tests can't open Room and there are no instrumented tests, so
  `MIGRATION_1_2` to `3_4` have never been run by a test. A failed migration is a crash loop that costs the outbox.
  Robolectric with Room's `MigrationTestHelper` should be able to run them on the JVM against the exported schemas —
  worth an hour to confirm.
- **No test of `SyncEngine` itself.** The pieces are pinned (`BatchSender`, `SyncLimits`, `SyncWire`); the
  orchestration — record, prune, send, extras, heartbeat — is not. The same Robolectric setup with a fake
  `ApiService` would cover it, including the circuit breaker from item 2.
- **Six monitors repeat one skeleton**: a scope, a mutex, `install` / `kick` / `afterSync` / `evaluateSafely`, and the
  "replace the recheck job without cancelling myself" block. A small shared runner would remove a few hundred lines
  and make item 4's fix one change instead of three.
- **`MainActivity` is 660 lines**, with the chip-group setup written four times. A helper for "chips for these values,
  this one checked, call back on change" shortens it; splitting the nudges onto their own screen (see *UX*) shortens
  it more.
- **Small inefficiencies.**
  - `PushRegistrar.enqueue` schedules a WorkManager job after every sync and on every app start, just for the worker
    to find the registration isn't due. Checking the stored time first avoids about a hundred jobs a day.
  - `BudgetMonitor.sittings` re-reads the usage log from the start of the day on every evaluation; late in the day
    that is the whole day's events each time a budgeted app comes to the front.
- **Lint's 121 warnings are mostly noise**: 56 `UseKtx`, 17 `PluralsCandidate`, 12 `GradleDependency`, 9
  `HardcodedText`, 8 `ApplySharedPref` (the `commit()` calls, which are deliberate), 6 `NewerVersionAvailable`. A
  `lint.xml` that turns off the deliberate ones would leave a list worth reading.
- **CLAUDE.md is long** (over 400 lines, much of it per-feature behaviour that the KDoc also states). It is loaded
  into every session. Keeping the rules there and moving the per-feature sections to `docs/` would cut that cost and
  halve the places a behaviour change has to be written down.

## Suggested order

1. Items 1, 3, 5, 6, 7 together: small, independent, no behaviour to decide.
2. Item 4, with the shared monitor runner if that refactor is wanted.
3. Item 2, after deciding which guard (breaker, body check, or both).
4. CI and the Robolectric tests (migrations, `SyncEngine`).
5. The diagnostics screen, then a device pass over the six unverified features.
6. The status-screen reshape.
